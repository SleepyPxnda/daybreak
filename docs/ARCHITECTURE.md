# Architecture

## Overview

Single-user Nuxt 4 app: Vue frontend (SSR, shadcn-vue) and Nitro REST API in one process, data in one SQLite file. Business logic lives as pure functions in `shared/utils/` and is used by client and server.

```
Read:     page/component → composable (useDay, useAccounts …) → useFetch(url, { key }) ─┐
Mutate:   page/component → runAction(() => api(url, { method, body }), KEYS) ────────────┤
                                                                                      ▼
Nitro:    middleware 00.migrations → 01.auth (Basic Auth) → server/api/<route>.<method>.ts
          → zod (readValidatedBody / getValidatedQuery / idFromRoute) → server/utils + shared/utils
          → drizzle (db from server/db/client.ts) → SQLite (DATABASE_URL)
Back:     JSON → runAction() shows errors as a toast, refreshNuxtData(KEYS) reloads the affected useFetch keys
```

## Structure

- `app/pages/` – one file per screen, file-based routing. Loads data via `useFetch`/composables, no business calculations.
- `app/components/` – own components in PascalCase; dialogs and inputs at the top (`*Dialog.vue`, `NumberInput`, `TimeInput`), one subfolder per area (`timeline/`, `quick-input/`, `widgets/`, `todos/`, `notes/`, `calendar/`, `overview/`), imported explicitly. `ui/` is generated by shadcn-vue – add only via CLI/MCP, never by hand.
- `app/composables/` – shared reads (`useFetch` with a fixed `key`) and the `*_KEYS` refresh lists; `runAction()`/`apiErrorMessage()` in `useRunAction.ts`.
- `app/utils/` – client-only helpers: `api.ts` (untyped `$fetch`), timeline geometry (`timeline.ts`, tested), markdown, account colors.
- `app/lib/utils.ts` – only shadcn's `cn()`; add nothing here.
- `server/api/` – one file per route (`index.get.ts`, `index.post.ts`, `[id].patch.ts`, `[id].delete.ts`, actions as `<verb>.post.ts`). May use `db` directly.
- `server/db/` – `schema.ts` (all tables), `client.ts` (libsql + drizzle, `DATABASE_URL`), `migrate.ts` (once per process).
- `server/utils/` – auto-imported in routes: per-entity zod schemas, shared DB queries (`loadSettings`, `checkAliases`, `resolveAssignment` …), error/param helpers (`params.ts`), `basicAuth.ts`.
- `server/middleware/` – `00.migrations.ts` (waits for migrations), `01.auth.ts` (Basic Auth). `server/plugins/` – migrations at startup, warning without a password.
- `shared/utils/` – pure business logic without DB/network (parser, target hours, balance, vacation, template materialization, booking notifications) plus shared base zod schemas (date, time, settings).
- `drizzle/` – generated migrations (`pnpm db:generate`), never edited by hand except the SQL file of a `--custom` migration for data changes. `scripts/seed.mjs` – dev test data (`pnpm db:seed`, empties the DB).
- `tests/` – flat `*.test.ts`, Vitest in Node; covers `shared/utils`, `app/utils/timeline.ts`, `server/utils/basicAuth.ts`. No route or component tests; DB only for migrations (`tests/migration.test.ts`).

## Data

- **SQLite** (`server/db/schema.ts`): `account` → `task` (exactly one account) → `block` (time range on one day, with `taskId` or directly `accountId`); `template` + `template_exception` (recurring blocks, materialized when `/api/blocks` is read); `day` (only deviations from a normal workday); `todo` (reminder, waiting-for, daily topic); `note`; `vacation_entitlement`; `settings` (key/JSON value).
- **Settings**: `loadSettings()` fills missing values from the defaults and drops invalid single values (`safeParse`); the balance start date is fixed on first read.
- **Derived, not stored**: target, balance, vacation status, overview – computed per request from blocks/days/settings (`shared/utils`).
- **Client**: no store (no Pinia). Shared state = Nuxt's `useFetch` cache under fixed keys (e.g. `'balance'` in layout and `useDay`); one `useState` (palette open); `localStorage` only for booking-notification state.
- Formats: date as `YYYY-MM-DD` string, time as minutes since midnight on the 15-minute grid, day boundaries in `Europe/Berlin` (process TZ).

## Boundaries

- The client talks to the server only over HTTP (`useFetch` to read, `api()` to mutate); never imports `server/`. Both sides may use `shared/utils`; `shared` imports neither `app/` nor `server/`.
- Validation only at the route with zod (body, query, params); `shared/utils` expects valid values.
- Errors: the server throws `createError({ statusCode, statusMessage })` with a German message (404 via `notFound`, UNIQUE → 409 via `isUniqueViolation`); the client shows it as a toast via `runAction()`.
- Side effects (DB writes, template materialization, migrations) only on the server; browser notifications only in `useBookingNotifications`.
- No external services; access protection only via Basic Auth on the server.

## Decisions

Dates are commit dates (the original docs are undated).

- 2026-09-28 – Stack Nuxt 4 + shadcn-vue/Tailwind v4 + Drizzle/SQLite + zod + Vitest, pnpm – one process, one file, self-hostable.
- 2026-09-28 – `@libsql/client` instead of better-sqlite3 – no native compilation on Windows; binary shipped via `nitro.externals.traceInclude`.
- 2026-09-28 – Migrations via Nitro plugin + middleware at startup instead of a migrate script – same path locally and in the container, no drizzle-kit at runtime.
- 2026-09-28 – Optional Basic Auth via `DAYBREAK_PASSWORD`, `/api/health` exempt – single user, no login system.
- 2026-09-28 – Dark only (`class="dark"` fixed), self-hosted fonts, no PWA – local tool, works offline.
- 2026-09-28 – Mutations through untyped `api()` – Nitro's route type inference hits "excessive stack depth" on dynamic URLs.
- 2026-09-28 – Templates materialized on read; `day` stores only deviations.
- 2026-09-29 – Docker image only on releases, multi-arch amd64/arm64.
- 2026-10-05 – Booking notifications as pure function, state only in `localStorage`.
- 2026-10-22 – Redesign to the cloudypanda brand: Geist, amber as the only accent, layers instead of shadows.
- 2026-11-19 – All code in English, only the UI in German – one language in code; the existing German names (code, file names, page URLs, API paths, DB tables, columns and stored values) were renamed in a dedicated refactor.
- 2026-11-19 – Data migrations: stored values and settings keys are rewritten by a `pnpm db:generate --custom` migration (`drizzle/0005_english_values.sql`) whose SQL file is written by hand; snapshots and `_journal.json` are never edited. `tests/migration.test.ts` is the one DB test: a one-way migration of the only data file needs proof that no rows, values or settings are lost.
- 2026-11-19 – drizzle-kit dropped the `RENAME COLUMN` statements for the rebuilt (not renamed) tables `block` and `todo`, so 16 lines were added by hand to `drizzle/0004_english_names.sql`. Lesson: after `db:generate`, check that every RENAME is present for rebuilt tables; the migration test catches it.
